## 1. 要解决的实际用户问题

| 用户问题 | 现状证据 | 不解决的后果 |
|---|---|---|
| 「库里的标签到底有哪些？」无法整体查看 | `api.ts: tags(limit=30)`，标签云只有前 30 条；B06 实测新标签被老语料挤出，点不到 | 行业包打了几十个 key 后，用户只能看到最近/最高频的 30 个 |
| 想按标签找图，得先知道准确值 | `engine-search` 是 `value = ?` 全值精确匹配；值是 `key-值` 形态后手工输入成本极高 | 打标产生的标签"存得下、用不上"，统计/筛选价值归零 |
| 同义碎片无法收拾 | 自由值没有词表约束（`白色`/`白`/`纯白`） | 计数被碎片切碎，标签越多越没用 |

结论：**需要"全量标签可见 + 可搜可筛"这一个能力，但不需要"第二个标签云"**。标签云保持摘要角色（侧栏快捷入口），全量浏览放到独立视图，输入侧补候选——三者共用同一数据源。

## 2. 是否新增独立页面（关键裁决）

选 **独立路由 `/tags`，但不进主导航**：

- 需要两栏（key 分组 × 值列表）+ 分页 + 多选批量 → Drawer 装不下；
- 低频但必要时要用（清理同义碎片），符合「按频率分层：低频收进按需打开的视图」；
- 不占一级导航，符合「导航只留浏览/处理两区」与「一个能力只归一个区域」——入口统一从图库侧栏「标签（N）→ 全部标签」和命令面板进入；
- 深链可达（`/tags?key=尺寸`），便于分享与回归测试。

被否方案：
- ❌ 标签云扩成 500 条：侧栏 240px、且没有搜索/分组/批量，问题只解决一半。
- ❌ 标签管理做成设置项：属于日常浏览/整理，不属于系统配置。
- ❌ 三级以上标签树：`key-值` 已提供两级语义，层级树会引入"路径标签"歧义（与目录职责重叠）。

## 3. 多行业场景差异

| 场景 | 标签量级 | 关键需求 | 本方案覆盖方式 |
|---|---|---|---|
| 电商/制造（品类×型号×规格） | 10³–10⁴ | 按 key（品类/规格）分组浏览、合并同义、按值筛图 | key 分组栏 + 值列表 + 批量合并 |
| 媒体/版权（人物、场景、授权） | 10²–10³ | 快速按人物/场景筛，看样本图确认 | 值行显示 3 张样本缩略图 |
| 品牌/市场（活动、渠道、地区） | 10¹–10² | 前缀联想、随手新增 | TagPicker 前缀候选 + 允许新建值（受控提示） |
| 个人/小团队 | <100 | 不想要管理界面 | 默认折叠，只在侧栏标签云用；不打扰 |

> **口径澄清（勿误读为"分行业实现"）**：上表描述的是**量级与使用方式的差异**，不是代码分支。
> 全产品只有**一套实现**（同一个 `/api/library/tags` + 同一个 TagPicker + 同一个 `/tags` 页面），
> 行业之间只差三样**数据驱动的参数**，且都由「标签总量/标签数」这类实测值触发，不由"行业"这个标签判断：
> ① 侧栏标签云摘要条数（默认 30，标签多时提示"查看全部"）；
> ② `/tags` 的默认分组与排序（按 key 计数 vs 按值计数）；
> ③ 行业包预置的 key 集合与受控词表（电商=品类/规格，媒体=人物/场景，品牌=活动/渠道）。
> 禁止出现 `if industry == "电商"` 这类逻辑；样本缩略图、分页、合并工具对所有行业一律存在（只是低量时不显眼）。

## 4. 操作流程（入口 → 处置 → 边界）

**A. 看全量**
侧栏「标签（137）→ 全部标签」或命令面板 `>标签` → `/tags`（左 key 列表带计数，右该 key 的值列表带计数与样本图）→ 点值 = 回图库并带 `tag=` 筛选（`/` 根路径 + 参数，不新开浏览语义）。

**B. 找标签（输入侧）**
任何需要标签的输入（搜索页过滤、图库筛选、检查器打标、批量打标、行业包配置）统一用 `TagPicker`：
输入即查（默认前缀，≥1 字符触发，250ms 防抖）→ 候选按 `-` 前 key 分组，显示 `值 × 计数` → ↑↓ 选择 / Enter 确认 / Esc 关闭 → 手输全值仍精确命中（候选为空时提示「无匹配标签，回车将作为新标签」——仅打标场景允许新建，筛选场景不允许）。

**C. 清理（低频动作）**
`/tags` 勾选多个值 → 「合并到…」（选目标值）→ 确认框列出影响资产数 → 执行；「改名」等价合并到新值。删除仅当计数为 0，否则先合并。
安全：一次操作 ≤5000 资产，超出要求分批；执行前给计数，执行后给回执（affected）。

**边界（明确不做）**
- 不做标签颜色/图标/收藏（v1 不做，纯靠计数排序）。
- 不做层级 >2、不做标签版本历史（audit 表只记合并前后 value 与计数）。
- 不做数值聚合（`尺寸-1200mm` 求平均属于导出层）。
- 标签云永远只作摘要：超过 30 条时显示「仅显示前 30 / 查看全部」。

## 5. 实现拆分（4 步，可独立验收）

1. **API 统一（唯一真源）**：`GET /api/library/tags?prefix=&key=&limit=&offset=` → `{items:[{value,key,count}], total, hasMore}`；
   索引：`idx_tag_value(value)` 已存在，prefix 用 `value LIKE 'p%'`（前缀可走索引），`COLLATE NOCASE` 匹配；
   key 过滤 = `value LIKE 'key-%'`，禁止全表扫（`EXPLAIN QUERY PLAN` 必须显示索引）。
2. **TagPicker 组件**：受控输入 + 候选面板（分组、计数、键盘可达、ARIA combobox），替换现有多处裸 input。
3. **`/tags` 页面**：两栏 + 搜索框 + 分页（50/页）+ 样本缩略图 + 多选批量（合并/改名/删除）+ 确认与回执。
4. **入口接线**：侧栏「标签」标题行加「全部 →」；命令面板加 `标签总览`；深链 `/tags?key=`；面包屑回 `/`。

## 5.5 前缀匹配算法与索引（性能设计）

**核心：两条查询分开，别在明细表上做候选。**

| 场景 | 数据源 | 算法 | 复杂度 |
|---|---|---|---|
| 前缀候选 / key 分组 / 计数列表 | **字典表** `tag_dict(value PK, key, count)`（distinct 值，10³–10⁴ 行） | B-tree **范围扫描**：`value >= 'p' AND value < 'p'‖0x10FFFF`，稳定排序 `(count DESC, value ASC)`，keyset 分页 | O(log V + k)，V=distinct 值数 |
| 点值→出图（筛选/计数真值） | 明细表 `tag(assetId, value)` | 覆盖索引 `idx_tag_value_asset(value, assetId)` 索引内连接 | O(matches) |
| 模糊/子串（非本期） | — | FTS5 trigram（值内 `_` 连接使分词无用） | 不做 |

关键点：

1. **不用 `LIKE 'p%'`**。SQLite 的 LIKE 优化只在 `case_sensitive_like=ON` 且列 collation 为 BINARY 时生效；
   默认设置下实测退化为**覆盖索引全扫描**（7.5M 行：`SCAN tag USING COVERING INDEX`，220.8ms）。
   显式范围 `>= / <` 则是 `SEARCH ... (value>? AND value<?)`，同一查询 **28.1ms**（窄 5 行）。
2. **大小写**：入口归一化时统一（ASCII lower，CJK 不变），比较用 BINARY；**不建 COLLATE NOCASE 索引**
   （两套比较语义会让索引选择变差）。真需要大小写不敏感时，存一列 `value_norm` + 独立索引，不改主索引。
3. **计数增量维护**：`tag_dict.count` 在打标写入/删除/合并的同一事务里 `+1/-1`（合并时对受影响 value 重算），
   避免每次 `COUNT(*) GROUP BY value` 扫明细。750 万行实测前缀分组 191ms、单值筛选 1.3ms —— 有了字典表后
   候选路径降到亚毫秒，且与库大小无关（只与 distinct 值数相关）。
4. **热缓存留到必要时**：V ≤ 10⁴ 时磁盘范围扫描已足够（微秒–毫秒）。若日后要压到零等待，再把 `tag_dict`
   全量载入进程内前缀映射（写时按版本号失效）；**不提前做 Trie**，避免"内存索引 + SQLite"两套真源。
5. **一致性**：`tag_dict` 由写路径维护，另提供 `POST /api/maintenance/rebuild-tag-dict`（幂等，`SELECT value, COUNT(*) GROUP BY value` 重建）+ 启动时校验 `SUM(count) == COUNT(tag)`，不一致自动重建。
